## 1. 프로젝트 소개


**Outstanding Spots**는 한국뉴욕주립대학교 학생들이 학교 주변의 제휴 매장과 할인 혜택을 쉽고 빠르게 확인할 수 있도록 개발한 **지도 기반 제휴 매장 플랫폼**입니다.


지도에서 제휴 매장의 위치를 확인하고, 검색과 카테고리 필터를 통해 원하는 매장을 탐색할 수 있습니다. 각 매장의 할인 혜택, 영업시간, 위치 등의 상세 정보를 제공하며 글로벌 캠퍼스 환경을 고려해 한국어와 영어를 지원합니다.


단순한 매장 조회를 넘어 **학생 · 제휴 매장 사장님 · 관리자별 사용자 환경**을 구축했습니다.


학생은 관심 매장을 저장하거나 최근 확인한 매장을 다시 찾아볼 수 있고, 사장님은 승인된 본인의 담당 매장의 정보를 관리할 수 있습니다. 관리자는 전체 매장과 사장님 가입 신청을 관리할 수 있습니다.

---


## 2. 시작 배경


한국뉴욕주립대학교의 동아리 **Outstanding**은 학생들이 학교 주변의 다양한 매장에서 할인 혜택을 받을 수 있도록 제휴 매장을 발굴하고 계약해 왔습니다.


하지만 제휴 매장이 약 **50곳 이상**으로 증가하면서 기존 Excel 기반 정보 전달 방식에는 한계가 생겼습니다.


Excel은 매장 정보를 관리하기에는 적합했지만 학생이 실제로 매장을 이용하려는 순간,


- 현재 위치 주변에 어떤 제휴 매장이 있는지
- 원하는 종류의 매장이 어디에 있는지
- 어떤 할인 혜택을 받을 수 있는지
- 현재 영업 중인 매장인지


등을 빠르게 파악하기 어려웠습니다.


이 문제를 해결하기 위해 흩어져 있던 제휴 정보를 **지도 위에서 직관적으로 탐색하고 필요한 정보를 한곳에서 확인할 수 있는 웹 서비스**를 개발하게 되었습니다.

## 7. Trouble Shooting


### 7-1. 지도 렌더링 구조 및 성능 개선


### Problem


지도는 매장 데이터 변경과 사용자 상호작용에 따라 많은 마커를 지속적으로 관리해야 했습니다.


지도와 마커의 상태가 React 렌더링 과정과 불필요하게 결합되면 동일한 계산이나 객체 처리가 반복될 수 있고, 이는 지도 중심 서비스의 사용자 경험에 직접적인 영향을 줄 수 있었습니다.


### Solution


지도 및 마커 렌더링 구조를 정리하면서 React의 렌더링 생명주기와 지도 객체의 생명주기를 분리하는 방향으로 개선했습니다.


- `useRef`를 활용해 렌더링과 직접 관계없는 지도 관련 상태 관리
- `useMemo`를 활용해 반복 계산이 필요한 값의 불필요한 재계산 최소화
- 지도와 개별 Marker의 책임 분리
- 지도 상태 변경에 필요한 effect의 의존 관계 정리
- 불필요한 JavaScript 및 지도 관련 코드 정리

### Result

지도와 Marker의 책임을 분리하고, 렌더링과 직접 관련되지 않은 값과 반복 계산되는 값을 각각 `useRef`, `useMemo`로 관리하면서 **지도 상태 변화에 따라 필요한 로직만 실행되는 구조로 개선**했습니다.

특히 매장 데이터나 선택 상태가 변경될 때 지도 전체의 동작을 다시 처리하는 대신, **변경된 상태가 필요한 컴포넌트와 로직에만 반영되도록 지도 렌더링 흐름을 정리**했습니다.

이를 통해 지도 객체 관리, Marker 렌더링, 매장 선택 상태 등이 하나의 흐름에 복잡하게 얽히는 것을 줄이고, **각 컴포넌트의 역할과 상태 변경에 따른 동작을 보다 명확하게 파악할 수 있는 구조**로 개선했습니다.

이후 지도 관련 기능을 수정하거나 확장할 때도 전체 지도 로직을 함께 수정하기보다 **해당 기능을 담당하는 컴포넌트와 로직을 중심으로 변경할 수 있도록 유지보수성을 높였습니다.**

### 7-2. 지도 SDK 의존성 개선을 위한 Kakao Maps → Leaflet 전환

### Problem

초기에는 **Kakao Maps JavaScript SDK**를 사용해 지도 기능을 구현했습니다. 하지만 서비스를 운영하고 기능을 확장하면서 지도 SDK를 React의 렌더링 흐름과 함께 관리하는 과정에서 구조적인 복잡성이 커졌습니다.

특히 지도 SDK 로딩과 지도 객체 초기화, 매장 데이터 변경에 따른 Marker 생성·갱신을 직접 제어해야 했고, 컴포넌트가 다시 렌더링될 때 지도 관련 로직이 불필요하게 반복되지 않도록 별도의 상태 관리가 필요했습니다.

이를 해결하기 위해 SDK 로딩 Promise를 캐싱하고 `useRef`를 활용해 지도 초기화 여부를 관리하는 등 기존 구조를 최적화했지만, 서비스에서 실제로 사용하는 지도 기능에 비해 SDK에 종속된 초기화·객체 관리 로직을 계속 유지해야 한다는 문제가 남아 있었습니다.

Outstanding Spots에서 실제로 필요한 지도 기능은 다음과 같이 비교적 명확했습니다.

- 제휴 매장 위치 및 다수의 Marker 표시
- 매장 데이터 변경에 따른 Marker 갱신
- 현재 위치 표시
- 지도 이동 및 확대/축소
- Marker 선택과 매장 상세 UI 연동
- 모바일 환경에서의 지도 탐색

따라서 특정 지도 SDK에 맞춘 명령형 객체 관리 방식을 계속 확장하기보다, **React 컴포넌트 구조와 자연스럽게 결합할 수 있는 지도 기술로 전환하는 것이 장기적인 유지보수에 더 적합하다고 판단했습니다.**

### Solution

지도 구현을 **Kakao Maps JavaScript SDK에서 Leaflet + React Leaflet + OpenStreetMap 기반으로 전환**했습니다.

React Leaflet의 MapContainer, TileLayer, Marker API를 활용하고, 매장 마커 UI는 별도 Marker 컴포넌트로 분리했고, 지도 구성 요소를 React 컴포넌트 트리 안에서 관리하도록 변경했습니다.

기존에는 지도 SDK의 객체를 생성하고 데이터 변화에 맞춰 Marker 객체를 직접 추가·삭제·갱신해야 했다면, 전환 후에는 **매장 데이터를 React의 상태와 props로 전달하고 이를 기반으로 Marker 컴포넌트를 렌더링하는 구조**로 변경했습니다.

또한 지도와 Marker의 책임을 분리했습니다.

- `Map` 컴포넌트: 지도 컨테이너와 viewport 등 지도 전체 흐름 관리
- `Marker` 컴포넌트: 개별 매장의 위치와 Marker UI 관리
- React state / props: 매장 데이터와 선택 상태 전달
- `useRef`: 렌더링과 직접 관계없는 지도 객체 및 값 관리
- `useMemo`: 반복적으로 생성할 필요가 없는 지도 관련 값 재사용

이를 통해 **외부 지도 객체를 React 바깥에서 직접 관리하는 코드의 비중을 줄이고, 지도 UI 역시 다른 React UI와 동일한 컴포넌트 및 상태 흐름 안에서 관리할 수 있도록 구조를 단순화했습니다.**

### Result

지도 기술 전환을 통해 가장 크게 개선된 부분은 단순한 지도 라이브러리 변경이 아니라 **지도 기능을 관리하는 프론트엔드 구조**였습니다.

기존의 SDK 초기화와 Marker 객체 관리 중심 구조에서 벗어나 지도와 Marker를 React 컴포넌트 단위로 분리하면서, 매장 데이터 변경과 UI 상태가 지도에 반영되는 흐름을 코드에서 보다 명확하게 추적할 수 있게 되었습니다.

또한 특정 지도 SDK의 초기화 방식에 의존하던 코드를 줄이고, 지도에 필요한 기능을 서비스 요구사항에 맞춰 구성하면서 이후 지도 관련 기능을 수정하거나 확장할 때 영향을 받는 코드의 범위를 줄였습니다.

이 과정에서 **기술 선택은 기능 구현 가능 여부만으로 결정하는 것이 아니라, 실제 서비스가 요구하는 기능의 범위와 프레임워크와의 결합 방식, 장기적인 유지보수 비용까지 함께 고려해야 한다는 점**을 경험했습니다.

### 7-3. 역할별 관리 시스템 구축을 통한 운영 구조 개선


### Problem

초기 Outstanding Spots는 **학생이 제휴 매장 정보를 조회하는 기능을 중심으로 개발**되어, 실제 서비스를 운영하는 사장님이나 관리자를 위한 별도의 관리 환경이 존재하지 않았습니다.

이 때문에 매장의 할인 혜택, 영업시간, 소개 등의 정보가 변경될 때마다 **사장님이 직접 정보를 수정할 수 없었고, 모든 변경 요청을 개발자가 전달받아 처리해야 했습니다.**

운영 측면에서는 더 큰 문제가 있었습니다. 별도의 관리자 페이지가 없었기 때문에 개발자인 저 역시 웹에서 매장을 등록하거나 수정·삭제할 수 없었고, **MongoDB에 직접 접속해 데이터를 변경해야 했습니다.**

결과적으로 다음과 같은 운영상의 한계가 발생했습니다.

- 사장님이 자신의 매장 정보를 직접 관리할 수 없음
- 단순 정보 변경에도 개발자의 개입이 필요함
- 신규 매장 등록 및 기존 매장 수정·삭제 시 DB에 직접 접근해야 함
- 매장 수와 변경 요청이 증가할수록 개발자가 반복적인 운영 업무를 처리해야 함
- 서비스 운영이 특정 개발자에게 의존하여 확장하기 어려움

기능을 추가하는 것보다 먼저 **개발자가 직접 데이터를 수정해야만 운영되는 구조 자체를 개선해야 한다**고 판단했습니다.

따라서 학생에게 정보를 보여주는 서비스에서 나아가, **실제 서비스 운영 주체가 필요한 작업을 각자의 권한 범위 안에서 직접 처리할 수 있는 구조가 필요했습니다.**


### Solution


사용자를 학생 / 사장님 / 관리자로 구분하고 역할에 따라 사용할 수 있는 기능과 데이터 접근 범위를 분리했습니다.


- 학생: 개인 정보, 즐겨찾기, 최근 본 매장 관리
- 사장님: 관리자에게 사장님 로그인 권한이 승인될 시 본인 담당 매장 조회 및 수정
- 관리자: 전체 매장 CRUD 및 사장님 가입 승인/거절
- 인증이 필요한 요청에 대한 서버 측 권한 검증
- 권한이 없는 요청에 대한 접근 제한
- 세션 쿠키에 `HttpOnly`, `Secure`, `SameSite` 적용


### Result

기존에는 매장 정보 하나를 수정하기 위해서도 **사장님의 변경 요청 → 개발자 확인 → MongoDB 직접 수정**의 과정을 거쳐야 했지만, 역할별 관리 기능을 구축한 이후에는 각 사용자가 자신의 권한 범위 안에서 필요한 작업을 **직접** 처리할 수 있도록 운영 구조를 변경했습니다.

- **사장님**은 관리자 승인 후 본인이 담당하는 매장의 할인 혜택, 영업시간 등 매장 정보를 직접 수정할 수 있도록 했습니다.
- **관리자**는 DB에 직접 접근하지 않고 Admin 페이지에서 매장 등록·조회·수정·삭제할 수 있게 변경하였고 사장님 가입 승인/거절을 처리할 수 있도록 했습니다.
- **학생**은 매장 데이터를 조회하면서 즐겨찾기와 최근 본 매장 등 개인화 기능만 사용할 수 있도록 역할을 분리했습니다.
- 프론트엔드에서 화면과 기능을 구분하는 것에 그치지 않고 **서버에서도 사용자 역할과 담당 매장을 검증하여 허용된 데이터에만 접근할 수 있도록 제한**했습니다.

이를 통해 **모든 매장 변경 작업이 개발자를 거쳐야 했던 운영 병목을 줄이고, 개발자가 DB를 직접 수정하지 않아도 실제 운영 주체가 웹에서 서비스를 관리할 수 있는 구조로 전환**했습니다.

## 9. 운영 경험


Outstanding Spots는 개발 완료 후 종료한 프로젝트가 아니라 실제 한국뉴욕주립대학교 학생들이 사용하는 서비스로 운영하고 있습니다.


현재까지 **2,700명 이상의 사용자가 서비스를 이용했으며**, 약 **50개 이상의 제휴 매장 정보**를 제공해 왔습니다.


서비스를 직접 운영하면서 기능 개발뿐 아니라 성능 개선, 모바일 환경 대응, 배포, 인증 및 권한 관리, 데이터 관리 등 실제 서비스 운영 과정에서 발생하는 문제를 지속적으로 해결하고 있습니다.


이를 통해 기능을 구현하는 것에서 끝나는 것이 아니라 **사용자가 지속적으로 사용할 수 있는 서비스를 안정적으로 유지하고 개선하는 것까지 개발자의 책임**이라는 점을 경험했습니다.
