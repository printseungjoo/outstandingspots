## 1. 프로젝트 소개




**Outstanding Spots**는 한국뉴욕주립대학교 학생들이 학교 주변의 제휴 매장과 할인 혜택을 쉽고 빠르게 확인할 수 있도록 개발한 **지도 기반 제휴 매장 플랫폼**입니다.




지도에서 제휴 매장의 위치를 확인하고, 검색과 카테고리 필터를 통해 원하는 매장을 탐색할 수 있습니다. 각 매장의 할인 혜택, 영업시간, 위치 등의 상세 정보를 제공하며 글로벌 캠퍼스 환경을 고려해 한국어와 영어를 지원합니다.




단순한 매장 조회를 넘어 **학생 · 제휴 매장 사장님 · 관리자별 사용자 환경**을 구축했습니다.




학생은 관심 매장을 저장하거나 최근 확인한 매장을 다시 찾아볼 수 있고, 사장님은 승인된 본인의 담당 매장의 정보를 관리할 수 있습니다. 관리자는 전체 매장과 사장님 가입 신청을 관리할 수 있습니다.

## 2. 시작 배경




한국뉴욕주립대학교의 동아리 **Outstanding**은 학생들이 학교 주변의 다양한 매장에서 할인 혜택을 받을 수 있도록 제휴 매장을 발굴하고 계약해 왔습니다.




하지만 제휴 매장이 약 **50곳 이상**으로 증가하면서 기존 Excel 기반 정보 전달 방식에는 한계가 생겼습니다.




Excel은 매장 정보를 관리하기에는 적합했지만 학생이 실제로 매장을 이용하려는 순간,




- 현재 위치 주변에 어떤 제휴 매장이 있는지
- 원하는 종류의 매장이 어디에 있는지
- 어떤 할인 혜택을 받을 수 있는지
- 현재 영업 중인 매장인지




등을 빠르게 파악하기 어려웠습니다.




이 문제를 해결하기 위해 흩어져 있던 제휴 정보를 **지도 위에서 직관적으로 탐색하고 필요한 정보를 한곳에서 확인할 수 있는 웹 서비스**를 개발하게 되었습니다.

## 7. Trouble Shooting



### 7-1. React SPA → Next.js 16 App Router 마이그레이션으로 프론트엔드 아키텍처 개선


### Problem


초기 Outstanding Spots는 **Vite 기반 React SPA**였습니다. 학생 · 사장님 · 관리자 화면이 늘어나면서 다음과 같은 구조적 한계가 드러났습니다.


**1. 검색 유입 경로 부재**

Outstanding Spots는 로그인 뒤에 숨은 앱이 아니라 **학생들이 검색과 링크로 들어오는 공개 서비스**입니다. 하지만 SPA는 검색 엔진에 빈 HTML을 먼저 내려주고, 페이지별 제목 · 설명 · 구조화 데이터를 정적으로 관리할 수 없었습니다. 


**2. 화면 추가 비용 증가**

- 모든 경로가 **라우팅 설정 한 파일**에 모여 있어 화면이 늘어날수록 설정과 화면 구조가 강하게 결합됨
- 학생 · 사장님 · 관리자 영역마다 **헤더, 내비게이션, 인증 확인이 페이지별로 복제**되어 새 화면 하나를 추가할 때 같은 코드를 반복해서 작성해야 함
- 역할별 접근 제어 코드가 여러 곳에 흩어져 권한 정책을 바꾸기 어려움


**3. 브라우저 전용 코드와 렌더링 구조의 혼재**

지도(`window` · DOM 의존)와 일반 화면이 한 번들 안에 섞여 있어, 지도 때문에 페이지 전체를 브라우저에서만 그릴 수밖에 없었습니다.


단순히 SEO 태그를 덧붙이는 방식으로는 **라우팅 · 레이아웃 · 렌더링 경계가 한 덩어리인 구조 자체**를 해결할 수 없다고 판단해, 파일 기반 라우팅과 중첩 레이아웃, 서버 렌더링을 제공하는 **Next.js App Router로 전환**하기로 결정했습니다.


### Solution


기존 **Express API와 MongoDB는 그대로 두고 화면 구조만 이전**했습니다.


- **파일 기반 라우팅으로 경로 관리 일원화**
  - `app/` 폴더 구조가 곧 URL 구조가 되도록 정리 (`/`, `/stores`, `/login`, `/signup/*`, `/student/*`, `/owner/*`, `/admin/*`)
- **역할별 중첩 레이아웃으로 공통 코드 한 곳에서 처리**
  - `app/student`, `app/owner`, `app/admin`에 각각 `layout.tsx`를 두고 헤더 · 내비게이션 · 접근 가드(`Protected*Route`)를 레이아웃 단위로 적용
  - 하위 페이지는 인증 확인과 공통 UI를 다시 작성하지 않음
  - 마이페이지 · 관리자 영역은 `robots: noindex` 메타데이터를 레이아웃에서 일괄 지정
- **Metadata API와 구조화 데이터로 SEO 정비**
  - 루트 레이아웃에서 기본 메타데이터 · Open Graph · canonical · JSON-LD(`WebSite`) 제공
  - `/stores`, `/login` 등 페이지별 `metadata`를 서버에서 렌더링
- **브라우저 전용 컴포넌트 분리**
  - `window`에 의존하는 React Leaflet 지도를 `dynamic(..., { ssr: false })` 클라이언트 경계로 분리
  - 페이지 뼈대와 메타데이터는 서버에서 먼저 전달하고, 지도는 브라우저에서 이어서 로드
- **전역 상태와 스타일 구조 정리**
  - `AppShell`에서 언어 · 인증 · 매장 컨텍스트를 한 번만 제공
  - styled-components 레지스트리를 구성해 서버 렌더링 시 스타일을 HTML에 포함
- **안전한 전환 절차**
  - 전환 중 깨질 수 있는 지도 탐색, 로그인, 매장 관리 흐름은 Playwright 회귀 테스트 통과를 기준으로 단계적으로 진행
  - `output: 'standalone'` 빌드로 배포 산출물 구성


### Result


| 항목 | Before (React SPA) | After (Next.js App Router) |
| --- | --- | --- |
| **라우팅** | 라우팅 설정 파일 한 곳에 집중 | 폴더 구조 = URL 구조 |
| **새 화면 추가** | 레이아웃 · 인증 확인 코드 반복 작성 | 폴더 + `page.tsx`만 추가 |
| **역할별 공통 UI · 가드** | 페이지마다 복제 | 역할별 `layout.tsx` 한 곳에서 처리 |
| **페이지별 메타데이터** | 관리 불가 | Metadata API로 페이지 단위 관리 |
| **브라우저 전용 코드** | 전체 화면과 한 번들에 혼재 | 지도만 클라이언트 경계로 분리 |
| **Lighthouse SEO** | 83 | **100** |
| **Lighthouse Best Practices** | 31 | **92** |

> Lighthouse 수치는 메타데이터와 구조화 데이터 정비 기준의 localhost 측정값입니다.


결과적으로 **라우팅 · 레이아웃 · 접근 제어 · 렌더링 경계가 한 덩어리였던 SPA 구조를, 역할 단위 레이아웃과 파일 기반 라우팅으로 분리**했습니다. 기능이 늘어도 화면 하나를 추가하는 비용이 일정하게 유지되고, 검색 엔진이 읽을 수 있는 HTML과 페이지별 메타데이터를 제공하는 구조로 전환했습니다.

### 7-2. Kakao Maps SDK를 React Leaflet으로 전환해 중복 로드와 재초기화 제거


### Problem


초기 Outstanding Spots의 지도는 **Kakao Maps JavaScript SDK를 직접 로드하고 지도 인스턴스와 마커를 명령형으로 제어하는 방식**으로 구현되어 있었습니다.


서비스에 점점 기능과 지도와 연결되는 상태가 늘어나면서 **React의 상태 관리와 Kakao Maps의 지도 객체 생명주기를 별도로 관리해야 하는 구조적 복잡성**이 커졌습니다.


초기 구조에서는 지도 관련 컴포넌트에서 SDK 로딩과 지도 초기화를 직접 처리했기 때문에 다음과 같은 문제가 있었습니다.


- 여러 지도 관련 로직에서 SDK의 로드 여부와 초기화 상태를 직접 관리해야 함
- React 상태 변경과 외부 지도 객체의 생명주기를 별도로 동기화해야 함
- 카테고리 및 검색 결과가 변경될 때 기존 마커 제거와 새로운 마커 생성을 직접 처리해야 함
- 지도 초기화, 마커 갱신, 사용자 인터랙션 로직이 서로 강하게 연결됨
- 지도 기능이 확장될수록 명령형 지도 제어 코드와 React 상태 관리 코드가 함께 복잡해짐


먼저 기존 Kakao Maps 구조를 유지하면서 **SDK 로드 Promise를 캐싱해 중복 로드를 방지하고, `useRef`를 이용해 지도 중복 초기화를 막는 방식으로 개선**했습니다.


하지만 개별 문제를 최적화하는 것만으로는 **React와 별도로 지도 객체의 생명주기를 관리해야 한다는 구조적 복잡성 자체는 해결하기 어렵다**고 판단했습니다.


따라서 Kakao Maps SDK를 계속 최적화하는 방법과 지도 라이브러리를 전환하는 방법을 비교하고, **React 컴포넌트 생명주기 안에서 지도와 마커를 관리할 수 있는 React Leaflet으로 전환**하기로 결정했습니다.


### Solution


Kakao Maps SDK를 직접 로드하고 지도 객체를 생성하는 구조를 제거하고, **Leaflet + React Leaflet + OpenStreetMap 기반으로 지도 렌더링 구조를 재구성**했습니다.


- Kakao Maps SDK 직접 로딩 구조 제거
- 기존 SDK 로드 Promise 캐싱 및 `useRef` 기반 초기화 제어 구조 제거
- `MapContainer`를 중심으로 지도 자체를 React 컴포넌트로 관리
- 지도와 Marker의 책임을 React 컴포넌트 단위로 분리
- 매장 데이터를 기반으로 Marker가 선언적으로 렌더링되도록 구조 변경
- 검색 및 카테고리 상태와 지도 표시 데이터를 React 상태 흐름 안에서 연결
- 필터링 결과는 `useMemo`를 활용해 관련 조건이 변경될 때만 재계산


이를 통해 **외부 SDK 객체의 상태를 React와 별도로 동기화하는 방식 → React의 상태 변화에 따라 지도 UI가 렌더링되는 구조로 변경**했습니다.


### Result


기존에는 SDK 로딩 여부, 지도 인스턴스, 마커 생성·제거 등을 직접 관리해야 했지만 React Leaflet 전환 이후에는 **지도와 마커를 React 컴포넌트 단위로 관리할 수 있는 구조로 단순화**했습니다.


- **지도 초기화**를 직접 SDK 로드 및 DOM 기반으로 처리하던 구조에서 `MapContainer` 기반 선언형 구조로 변경
- **마커 관리**를 직접 생성·제거하는 방식에서 매장 데이터에 따라 React 컴포넌트가 렌더링되는 방식으로 변경
- 지도와 Marker의 책임을 분리하여 지도 기능 변경 시 영향을 받는 코드 범위 축소
- 검색·카테고리 등 상태 변화와 지도 렌더링을 React 데이터 흐름 안에서 관리
- `useMemo`를 적용해 필터 조건이 변경되는 경우에만 표시할 매장 목록을 재계산
- Kakao Maps SDK 로딩 및 초기화 상태를 관리하기 위한 별도 코드 제거


결과적으로 **Kakao Maps SDK의 중복 로드와 초기화를 개별적으로 방어하던 구조에서 나아가, 지도 생명주기 자체를 React 컴포넌트 구조 안에서 관리하도록 전환**했습니다.


이를 통해 지도 기능이 추가될수록 복잡해지던 **SDK 초기화 → 지도 객체 관리 → 마커 직접 갱신** 구조를 **상태 변경 → React 렌더링** 중심의 구조로 단순화하여 지도 관련 코드의 유지보수성과 확장성을 높였습니다.

### 7-3. Playwright + GitHub Actions E2E 테스트 자동화로 오류 수정 커밋 7일 기준 16건 → 1건


### Problem


Outstanding Spots는 **혼자 개발하고 운영하는 서비스**라 기능을 하나 고칠 때마다 지도 탐색, 로그인, 매장 관리가 그대로 동작하는지 **직접 눌러 보며 확인**해야 했습니다.


화면이 학생 · 사장님 · 관리자 3개 역할로 늘고, 지도 · 인증 · 권한 · 다국어(한/영) · 모바일 대응까지 서로 엮이면서 다음과 같은 문제가 반복되었습니다.


- 한 곳을 수정하면 **다른 역할의 화면이나 권한 흐름이 깨져도 배포 전까지 알기 어려움**
- 수동 확인은 매번 범위가 달라 **회귀 오류를 놓치기 쉬움**
- React SPA → Next.js 전환처럼 **큰 구조 변경은 수동 확인만으로 진행하기 어려움**


기능을 더 추가하기에 앞서 **"고쳤을 때 기존 기능이 그대로인지"를 자동으로 확인할 수 있는 안전망**이 먼저 필요하다고 판단했습니다.


### Solution


**Playwright로 사용자 흐름 단위의 E2E 테스트를 작성하고, GitHub Actions에서 Push / PR마다 테스트가 자동실행**하도록 연결했습니다.


**1. 역할별 핵심 사용자 흐름 검증**

| 영역 | 검증 범위 |
| --- | --- |
| **지도** | 마커 표시, 카테고리 · 영업 중 필터, 매장명 · 테마 자동완성 검색, 매장 상세 진입, 즐겨찾기, 최근 본 매장 기록, 내 위치 이동 |
| **학생** | 이메일 인증 가입, 로그인, 즐겨찾기 · 최근 본 매장 목록, 회원정보 수정 |
| **사장님** | 휴대전화 인증 가입 신청, 승인 상태별 로그인, 담당 매장 조회 · 수정, 사진 업로드, 비밀번호 변경, 탈퇴 |
| **관리자** | 매장 등록 / 수정 / 삭제, 주소 기반 좌표 검색, 사장님 가입 승인 · 거절 · 대기 전환 |
| **권한** | 세션 없는 접근 시 `/login` 이동, 다른 역할 페이지 접근 차단, 새로고침 후 세션 유지, 로그아웃 |
| **다국어 · 반응형** | 한/영 전환 유지, 데스크톱(1440×900)과 모바일(Pixel 5) 레이아웃 |

**2. 실패 시나리오까지 검증**

- 로그인 API 404, 서버 다운, 잘못된 비밀번호, 승인 대기 · 거절 계정
- 매장 저장 / 삭제 / 즐겨찾기 요청 실패 시 화면 상태 유지와 오류 안내
- 매장 목록 로딩 실패 시 재시도 안내

**3. API Mock 기반의 안정적인 테스트 환경**

- `context.route`로 API 요청을 가로채는 **MockApi**를 구성해 실제 서버 · DB 없이 프론트엔드를 단독으로 검증
- 요청 로그를 기록해 *"어떤 요청이 어떤 본문으로 나갔는지"*, *"변경 없을 때 API를 호출하지 않는지"* 까지 확인
- 외부 네트워크 요청은 차단하고 이미지 · 지오코딩은 Mock으로 대체해 **항상 같은 결과가 나오도록** 고정
- 세션을 시드하는 헬퍼(`seedStudentSession`, `seedOwnerSession`)와 `alert` / `confirm` 다이얼로그 캡처 헬퍼로 테스트 코드 중복 제거


### Result


| 항목 | 테스트 구축 전 | 테스트 구축 후 |
| --- | --- | --- |
| **7일 기준 오류 수정 커밋** | 최대 **16건** | **1건** (**93.75% 감소**) |
| **회귀 확인 방식** | 직접 화면을 눌러 수동 확인 | Push / PR마다 자동 실행 |
| **테스트 규모** | - | 12개 스펙 파일, 200개 이상 시나리오 |


- **Next.js App Router 마이그레이션(7-1)** 같은 큰 구조 변경도 테스트 통과를 기준으로 단계적으로 진행
- 권한 · 실패 시나리오를 테스트로 남겨 두어, 이후 UI 개편 때도 역할별 접근 제어가 유지되는지 바로 확인

결과적으로 **"고치고 → 직접 확인하고 → 배포 후 제보로 다시 고치는" 흐름을, "고치고 → 자동 검증 → 배포"로 바꿔** 1인 운영에서도 기능 개선을 안정적으로 이어갈 수 있는 기반을 만들었습니다.

### 7-4. 지도 중심 UI 재설계로 매장 탐색 경험 개선


### Problem


초기 Outstanding Spots는 **지도와 카테고리 영역이 분리된 구조**로 구현되어 있었습니다.


사용자는 제휴 매장을 찾기 위해 카테고리 영역과 지도를 오가며 정보를 확인해야 했고, 원하는 매장을 찾으려면 여러 단계의 탐색이 필요했습니다.


특히 제휴 매장 수가 증가하면서 단순히 지도에 매장을 표시하는 것만으로는 사용자가 원하는 매장을 빠르게 찾기 어려워졌습니다.


다음과 같은 사용자 경험상의 한계가 있었습니다.


- 지도와 카테고리가 분리되어 있어 탐색 과정에서 시선과 조작 위치가 반복적으로 이동함
- 매장 이름을 알고 있어도 지도에서 직접 검색할 수 있는 기능이 부족함
- 매장 수가 증가할수록 지도에서 원하는 매장을 직접 찾아야 하는 탐색 비용 증가


기능을 단순히 추가하기보다 **사용자가 원하는 제휴 매장을 빠르게 찾는다는 핵심 목적을 중심으로 탐색 흐름 자체를 다시 설계해야 한다**고 판단했습니다.




### Solution


전체 화면을 **지도 중심 인터페이스**로 재구성하고, 매장 탐색에 필요한 기능을 지도 위에서 바로 사용할 수 있도록 배치했습니다.


그 외에도
- 지도와 분리되어 있던 카테고리 필터를 **지도 위 필터 UI**로 통합
- 매장명이나 테마명을 입력해 매장을 찾을 수 있는 **검색 기능** 추가
- 입력 과정에서 관련 매장을 바로 확인할 수 있도록 **자동완성 검색** 적용
- 사용자가 현재 이용 가능한 매장을 빠르게 찾을 수 있도록 **영업 중 필터** 추가


각 기능을 독립적으로 추가하는 것이 아니라 **검색 → 필터링 → 지도에서 위치 확인 → 매장 선택**이 하나의 화면 안에서 자연스럽게 이어지도록 탐색 흐름을 구성했습니다.


### Result


기존의 **카테고리 선택 → 지도 이동 → 직접 매장 탐색** 방식에서, 지도 화면 안에서 검색과 필터링을 바로 수행하는 **지도 중심 탐색 구조**로 변경했습니다.


- 지도와 카테고리를 하나의 화면에 통합하여 탐색 중 화면과 시선 이동 감소
- 자동완성 검색을 통해 매장명이나 테마명을 입력하는 과정에서 탐색 후보를 즉시 확인
- 영업 중 필터를 통해 현재 이용 가능한 매장을 별도로 탐색 가능


결과적으로 Outstanding Spots의 메인 화면을 단순히 **제휴 매장을 지도에 표시하는 화면**에서 **사용자가 조건에 맞는 매장을 직접 탐색하는 인터페이스**로 전환했습니다.


이를 통해 기능을 개별적으로 추가하는 데 그치지 않고, **사용자가 원하는 매장을 찾는 전체 과정에서 발생하는 불필요한 이동과 탐색 단계를 줄이는 방향으로 사용자 경험을 개선**했습니다.

## 8. 운영 경험




Outstanding Spots는 개발 완료 후 종료한 프로젝트가 아니라 실제 한국뉴욕주립대학교 학생들이 사용하는 서비스로 운영하고 있습니다.




현재까지 **2,900명 이상의 사용자가 서비스를 이용했으며**, 약 **50개 이상의 제휴 매장 정보**를 제공해 왔습니다.




서비스를 직접 운영하면서 기능 개발뿐 아니라 성능 개선, 모바일 환경 대응, 배포, 인증 및 권한 관리, 데이터 관리 등 실제 서비스 운영 과정에서 발생하는 문제를 지속적으로 해결하고 있습니다.




이를 통해 기능을 구현하는 것에서 끝나는 것이 아니라 **사용자가 지속적으로 사용할 수 있는 서비스를 안정적으로 유지하고 개선하는 것까지 개발자의 책임**이라는 점을 경험했습니다.
